## After D16 piece 2 — one timer per packet type (2026-10-12)

`[Config V4]` now sets `beaconFloodsInterval = 5s`, `routeFloodsInterval = 20s`
(the baseline's), and each node arms both. The prediction in `omnetpp.ini` held
exactly: every sensor creates 11 beacons and **3 route floods** (the baseline's
3), the sink none (it is in `Dests`); totals 88 / 24 (were 88 / 88). Queue
overflow **180 → 64**. The flood's accounting still closes: sent counters =
`send_down` = queue incoming = 618; `send_up` = accepted + duplicates = MAC Rx =
1684; `add_newEntry` 31; the sink consumes 66 of 112 created (was 68 of 176).
What still differs from the baseline: who originates (the sensors beacon, the
sink originates nothing) and the flood itself — differences 1 and 3 below,
both the model's by decision.

**Where they differ, and why (the first run, before piece 2):**
1. **Who sends beacons.** The baseline arms its beacon timer on the sink only. In
   v4 the pattern's creating event guards `x ∈ ND ∖ Dests`, the sink is in
   `Dests`, so the sensors send them and the sink cannot (B1, 2026-09-19).
2. **How often.** The baseline has two timers, beacons 5 s and routes 20 s. v4 has
   one 5 s timer, `handleSelfMessage` → `runEnabledEvents()`, which tries both
   creating events every tick.
3. **Rebroadcast.** The baseline never forwards control; v4 keeps the model's
   flood (D14 Q4), so its receive counts and its queue overflow are a flood's.
